# 得物个人进销存极简化——增量简版 PRD

## 1. 项目信息

- **Language**：中文
- **Programming Language**：沿用现有 Next.js 16 + TypeScript + Tailwind CSS；数据层支持 Supabase
- **Project Name**：`dewu_pms_simple`
- **PRD 类型**：现有项目增量需求，不做竞品分析
- **主要终端**：iPhone Safari / 添加到主屏幕

### 原始需求复述

将现有个人进销存简化为低点击工具：采购时主要录入商品进价；寄件时可批量选择商品、录入一笔总快递费并均摊；售出后录入实际到手价。允许删除误录商品，也能处理采购平台退货退款。现有数据可全部清空，从空白数据库重新开始。接入 Supabase 的主要目的，是减少 iPhone 本地存储占用并降低 Safari 清理本地数据造成丢失的风险，而不是主打跨设备。OCR 继续作为辅助录入，并评估成熟开源方案，但不能承诺无法验证的“精准识别”。

## 2. 产品定义

### 2.1 Product Goals

1. **极简录入**：完成一件商品从采购到结算的核心金额记录，常规场景只要求进价、均摊快递费、到手价三个金额。
2. **利润可信**：批量寄件的运费分摊总额必须与实际支付总运费完全一致，单件及合计利润可复算。
3. **数据可控**：支持误录删除、采购退货退款、全库清空，并将正式数据放到 Supabase，降低对 Safari 本地持久化的依赖。

### 2.2 核心业务口径

#### 极简金额输入

- **进价**：单件采购成本，必填，金额精确到分，必须 `>= 0`。
- **快递费**：发出一批商品实际支付的总运费；由系统均摊并写入每件商品，单件也可按一批处理。
- **到手价**：商品售出后实际到账金额，必填后才产生实际利润，金额精确到分，必须 `>= 0`。
- 商品名称/货号、尺码等仍用于区分实物，但不增加复杂财务字段；允许按现有最小校验保留。
- 平台费、平台补贴、其他费用、预计售价/利润不再出现在默认录入 UI；历史数据字段可兼容保留，新增记录默认均为 `0`/空。

#### 唯一利润公式

```text
单件实际利润 = 到手价 - 进价 - 该件均摊快递费
合计实际利润 = Σ单件实际利润
```

- 未录入到手价时展示“未结算”，不得展示为利润 `0`。
- 采购平台退货退款的商品不进入库存资金、销售额和利润统计。
- 全站金额计算必须以“分”为整数运算，展示时再格式化为元，避免浮点误差。

### 2.3 User Stories

1. As a 个人卖家, I want 只录入商品和进价 so that 我能快速建立单件库存。
2. As a 个人卖家, I want 一次选择多件商品并录入总快递费 so that 系统自动把运费准确均摊到每件商品。
3. As a 个人卖家, I want 售出时只填写到手价 so that 我可以立刻看到真实利润。
4. As a 个人卖家, I want 删除误录记录或标记采购退货退款 so that 库存和报表不被错误数据污染。
5. As a iPhone Safari 用户, I want 正式数据保存到 Supabase so that 本机少存数据且浏览器清理后仍可恢复。

## 3. 技术规范

### 3.1 Requirements Pool

#### P0 — Must have

1. **极简采购录入**
   - 默认财务必填项仅为单件进价；数量大于 1 时按单件库存生成。
   - 不展示采购运费、采购优惠等复杂成本 UI；新增商品的库存成本直接等于进价。
   - 保持现有 8 个状态任意直达，不新增强制流程。

2. **极简售出/结算录入**
   - 售出或结算时默认仅填写到手价；日期可默认当天。
   - 平台费、补贴、其他费用不显示，新记录按 `0` 处理。
   - 利润统一使用 `到手价 - 进价 - 均摊快递费`。

3. **批量寄快递与均摊**
   - 用户从库存列表进入批量模式，选择 `N >= 1` 件未删除、未采购退款的商品，点击“批量寄出”。
   - 弹层只需录入本次**总快递费**，展示选中数量及每件分摊预览；确认后一次提交。
   - 确认寄出默认将所选商品直达现有 `shipping`（发往得物途中）状态；不限制其原状态，提交前明确展示状态变化。
   - **舍入规则**：总运费先转成整数分 `T`，`q = floor(T / N)`，`r = T mod N`；按稳定顺序（`created_at` 升序，若相同再按 `id` 升序）排列，前 `r` 件分配 `q + 1` 分，其余分配 `q` 分。例如 ¥10.00 / 3 件 = ¥3.34、¥3.33、¥3.33。
   - 验收：每件分摊最多相差 ¥0.01；分摊合计必须严格等于总快递费；刷新页面后结果不变。
   - 重复对同一件商品提交寄件费时必须提示“覆盖原分摊值”并二次确认，不静默累加。
   - 批量提交应具备原子语义：全部成功或全部不生效，不能留下部分商品已更新。

4. **误录删除与采购退货退款**
   - **误录删除**：视为这条业务事实从未发生。用户可从商品/库存详情删除对应记录；二次确认后硬删除该单件及其销售、状态历史、附件关联。默认不保留业务审计记录。
   - 若删除的是某采购批次最后一件库存，系统应同时清理空采购批次；若商品资料已无任何库存/批次引用，再清理孤立商品资料，避免“空壳项目”。
   - 已售出/已结算记录也允许删除，但确认文案必须提示将影响历史利润和报表。
   - **采购平台退货退款**：视为真实发生过，不等同误录。将商品直达现有 `refunded` 状态，清除/作废销售结算数据，不计库存资产和利润；保留商品、进价、退款状态、操作时间及可选备注，形成轻量历史。
   - 已标记采购退款的记录仍提供“删除”入口，供用户明确决定彻底清除；删除后不保留审计。

5. **空数据库重置**
   - 设置页提供“清空全部数据”，删除 products、purchase_batches、inventory_units、sales、attachments、status_history 及对应图片对象。
   - 必须展示影响范围并进行高风险二次确认（建议输入“清空”）；成功后首页、库存、报表均为空态。
   - 本次改版允许用户先执行一次清空再开始使用；不要求把当前本地旧数据迁移到 Supabase。
   - 清空操作应全量成功或明确报告失败项，不得界面显示成功但残留业务数据。

6. **Supabase 正式存储**
   - 配置 Supabase 后，结构化业务数据和附件均以 Supabase 为正式数据源；本地只保留必要的会话配置、短期缓存和待提交状态，不保留第二份完整数据库。
   - 目标是减少 iPhone 本地占用、避免 Safari 清理 localStorage/IndexedDB 后业务数据丢失；产品文案不宣传多设备同步。
   - 首次加载、增删改、批量寄出、退款、清库均须实测；失败必须显示可重试错误，不可静默回退到本地库形成数据分叉。
   - 无网络时默认只读已缓存界面或明确提示“联网后操作”；P0 不承诺完整离线编辑。

7. **移动端可用性**
   - 390px 宽度无横向溢出；金额输入调用数字键盘；关键动作可单手完成。
   - 常规路径目标：新增商品核心金额不超过 1 个财务输入；批量寄出不超过“选择商品—输入总运费—确认”3 个主要步骤；结算不超过“输入到手价—确认”2 个主要步骤。

#### P1 — Should have

1. **OCR 可用性评测与增强**
   - 当前方案为浏览器端 `tesseract.js（chi_sim + eng）+ 正则`。可尝试识别：平台、实付/合计金额、数量、尺码、货号、订单号、品名。
   - 当前方案适合“给出候选值”，不保证稳定精准：低清/裁切截图、花字或浅色背景、列表中多个商品/价格、促销叠加、页面模板变化、长品名、货号与订单号混淆均可能出错。
   - OCR 结果必须先进入校对页；不得未经确认直接写库。低置信字段应留空或高亮，不猜测。
   - 对 GitHub 成熟开源方案开展小型技术验证，优先比较 PaddleOCR / RapidOCR 与现有 Tesseract.js 在中文订单截图、iPhone Safari 性能和部署成本上的表现。不得仅因 GitHub 星数直接替换。
   - PaddleOCR/RapidOCR 的中文与版面能力通常更适合服务端或转换后推理；若必须纯浏览器运行，应同时评估模型体积、首屏下载、内存、耗时和 Safari 崩溃风险。

2. **OCR 准确率验收定义**
   - 建立不少于 100 张脱敏真实订单截图的固定测试集，覆盖实际使用平台，每个平台建议不少于 20 张；截图必须包含清晰、裁切、长图、多商品、促销等真实难例。
   - “字段准确”定义为 OCR 最终候选值与人工标注**完全一致**；金额统一到分、空白与大小写可做标准化后比较。
   - `字段准确率 = 准确识别样本数 / 该字段清晰可见且存在的样本数`；另统计字段召回率和单张平均耗时，不能用少量演示截图宣称准确率。
   - 建议上线门槛：核心进价/实付金额准确率 `>= 95%`，数量与平台 `>= 95%`，尺码/货号/订单号 `>= 90%`，品名 `>= 80%`；未达标字段仍可作为候选，但不得自动回填。
   - iPhone Safari 验收：测试机上单张普通截图端到端处理建议 `<= 8 秒`，过程有进度提示，连续识别 5 张不崩溃。最终阈值以真实测试机基线校准。

3. **删除与重置安全补强**
   - 清库前可选导出 JSON 快照，作为用户主动备份；不因此阻塞清空。
   - 对刚完成的普通单件删除提供短时撤销；若实现成本较高，可后置，不替代二次确认。

#### P2 — Nice to have

1. 保存常用快递总价或最近一次金额，进一步减少输入。
2. 批量寄出生成可查看的“寄件批次”，支持按批次查看总运费与所含商品。
3. OCR 按平台维护模板化字段解析器，并允许用户反馈错误样本。
4. 数据用量提示，仅展示 Supabase 业务记录数/附件占用，不做复杂运维面板。

### 3.2 UI Design Draft

1. **新增页**
   - 保留识别商品所需的最少信息区；财务区只突出“进价”。
   - OCR 入口作为辅助按钮，识别后展示候选值与需人工确认的字段。

2. **库存页**
   - 卡片优先显示商品标识、状态、进价、已分摊快递费、到手价/利润。
   - 批量模式底部固定操作栏：`已选 N 件`、`批量寄出`、`改状态`；保留现有状态直达。

3. **批量寄出弹层**
   - 顶部：选中商品数量与缩略清单。
   - 中部：总快递费输入。
   - 下部：分摊预览、分摊合计、将变更至“发往得物途中”的提示。
   - 主按钮：`确认寄出并均摊`。

4. **售出/结算弹层**
   - 默认仅显示“到手价”和日期；实时展示利润预览。
   - 原复杂金额字段从默认 UI 移除，不以折叠高级项干扰个人常用路径。

5. **详情页**
   - 提供 `采购退货退款` 与 `删除此记录` 两个语义明确的操作，文案及结果不可混用。
   - 退款记录显示轻量时间线；误录删除成功后回到库存页。

6. **设置页**
   - 数据源状态：明确显示“Supabase 已连接/未连接”。
   - 危险操作区：`清空全部数据`，采用红色警示与二次确认。

### 3.3 核心验收场景

1. 新增进价 ¥100.00 的商品，批量寄件总运费 ¥10.00 / 3 件，系统写入 ¥3.34、¥3.33、¥3.33，合计 ¥10.00。
2. 其中一件录入到手价 ¥150.00，其利润分别按 `150.00 - 100.00 - 3.34 = 46.66` 展示；未录到手价的两件显示“未结算”。
3. 将一件标记采购退货退款后，它不进入库存资金与利润统计，但详情仍可看到退款时间和历史。
4. 删除一件误录商品后，关联销售、历史、附件不再可见，所有报表同步重算。
5. 清空全部数据后刷新，Supabase 与界面均为空；Safari 本地残留缓存不得还原旧业务记录。
6. 断网执行写操作时得到明确失败/待联网提示，不得出现 UI 成功而 Supabase 未写入。

## 4. 产品默认决策

为减少来回确认，本 PRD 默认采用以下口径：

- “到手价”即最终实际到账金额，不再拆售价、平台费、补贴。
- 进价为单件进价，不再计算采购运费/优惠分摊。
- 发往销售平台的快递费按本次所选单件均摊，并以分为单位保证总额守恒。
- 现有 8 状态和任意直达保留。
- 误录使用硬删除且不保留审计；真实采购退货退款保留轻量历史。
- 当前旧数据无需迁移，可直接清空；Supabase 为唯一正式业务数据源。
- OCR 只辅助录入、必须人工确认；先用真实样本评测，再决定是否替换引擎。

## 5. Open Questions（仅真正阻塞项）

1. **Supabase 接入实施与实测**：需要用户提供/配置可用的 Supabase 项目 URL、anon key，并允许执行迁移；在此之前无法完成真实云端写入、清库和附件删除验收。
2. **仅当 P1 决定采用服务端 OCR 时**：需确认是否允许订单截图上传到受控服务端处理，以及由何处承载 OCR 推理；若不允许，则固定采用纯浏览器方案，并接受准确率/性能上限。此问题不阻塞 P0 极简进销存。

除以上两项外，P0 可按本文默认口径实施，无需追加产品提问。
