# Supabase 验收、数据备份与离线体验设计

## 目标

在保持 Supabase 为唯一正式数据源的前提下，完成真实项目的登录与关键业务验收；为当前登录用户提供可下载的业务数据 JSON 备份和可确认的覆盖恢复；把应用壳升级为可安装、可在断网时明确提示的 PWA。

## 范围与非目标

- 包含：Magic Link 登录验收、采购/寄件/结算/退款、RLS、私有附件与清理队列的真实 Supabase 验证。
- 包含：商品、采购批次、库存单件、销售和状态历史的 JSON 导出与覆盖恢复。
- 包含：Service Worker 对 HTML、脚本、样式、图标等公开应用壳资源的预缓存与版本更新。
- 不包含：得物挂牌价编辑、离线写入队列、离线本地完整数据库、定时服务端备份、图片文件的导出或恢复。

## Supabase 验收

开发环境只使用项目根 URL（不使用 `/rest/v1/` 后缀）与 publishable/anon key；不使用或保存数据库密码、service role key 或其他高权限凭据。通过 Magic Link 使用指定测试账户登录。验收记录覆盖：认证回调、当前用户读写、RPC 原子写、跨用户 RLS 拒绝、private bucket 的 signed URL 读取，以及附件删除失败后的重试。

若需要发送 Magic Link，只有用户明确允许后才发送。验收使用可识别的临时测试记录，并在验收完成后由用户确认是否清理。

## JSON 备份

设置页提供“导出数据”操作。它读取当前认证用户的业务表，序列化为带 `schemaVersion`、导出时间和数据摘要的 JSON，并通过浏览器下载到用户设备。文件不含 Supabase URL、会话、密钥、密码或图片二进制。

备份的数据包括 products、purchase_batches、inventory_units、sales 和 status_history。附件元数据及 Storage 图片不纳入备份；因此从备份恢复后，历史图片不会恢复。

## 覆盖恢复

设置页允许选择 JSON 文件。导入分两步进行：先在浏览器中校验版本、字段和关联完整性并显示记录数量；用户输入“恢复”后二次确认。服务端恢复必须在单一 RPC 中执行，按当前 `auth.uid()` 作用域删除现有业务记录后按依赖顺序重新写入备份内容。失败时事务回滚，原数据不变。

由于该操作会覆盖当前账户数据，恢复页明确提醒：未包含附件图片，恢复后旧图片不会保留或恢复。恢复成功后刷新数据并显示结果摘要。

## 离线体验

新增 Service Worker 和 manifest 注册。缓存仅包括公开的应用壳资源、离线提示页和图标；缓存名按发布版本变更并清理旧应用壳缓存。不得缓存 Supabase REST/RPC/Auth 响应、signed URL、附件图片或用户输入。

断网时，若已加载的页面可由应用壳提供则显示“需要联网才能读取或修改数据”的提示；没有缓存的导航显示简洁离线页。所有写操作维持现有失败语义，不在本地排队或伪造成功。

## 验证

- 单元测试：备份格式化、导入校验、损坏文件/错误版本/跨表孤儿引用拒绝。
- 集成测试：恢复 RPC 的用户隔离、事务回滚、清空并重建语义。
- 浏览器测试：导出下载、导入预览与确认、断网加载离线页、禁止缓存 Supabase 请求。
- 真实 Supabase：完成登录、CRUD/RPC、RLS、private Storage 与清理队列检查，并明确记录任何依赖用户操作的步骤。

## 风险与决策

JSON 备份是针对误清空、误操作和迁移的手动恢复点，不表示 Supabase 会自然丢失数据。选择仅数据备份以降低移动端文件体积与复杂度；代价是恢复后不包含历史图片。离线缓存优先保证隐私和数据一致性，而非支持离线编辑。
